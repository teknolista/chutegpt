# Interactive analysis design

Design for IA-01–IA-07 and catalog S01–S22 in [PRODUCT](../product/interactive-strategies.md). The current binary uses Ratatui and Crossterm for the terminal and Calamine for XLSX; exact selected dependencies and Linux evidence are recorded below. MSRV and actual Windows/macOS support remain unverified.

Selected architecture, implemented in the current development application: source adapter -> validated immutable draw snapshot -> independently callable strategy functions -> typed results -> terminal presentation. Snapshot includes contest number, date, seven distinct numbers, month and optional prize fields, source path, hash and freshness provenance. Sorting is chronological; duplicate, missing, malformed and inconsistent contest numbers are rejected. Numeric months and Portuguese month names, including HTML entity variants, are accepted. Bytes and hash are frozen per analysis to avoid changing results during updates. These are implementation decisions, not PRODUCT requirements on language or framework.

Do not use unsafe Rust in project code unless specifically justified and reviewed; preserve terminal state by scoped cleanup. Propagate errors with actionable context. Worker and UI communication should bound memory, allow progress and cancellation and avoid sharing mutable analytical state. No network requests are required to process the local snapshot. Release artifacts and OS-specific terminal support must be checked on actual targets.

Owner decision: use a user data directory by default, allow a user-provided workbook path, and warn when no matching successful update was recorded on the local day or freshness is unknown. The existing updater writes to the repository docs directory; development invocation passes that path explicitly. Do not silently treat metadata for a different file as valid. Required and optional workbook columns are specified below; cross-platform path resolution is specified below as historical design, not validated support. Current Linux integration covers the documented workbook and sidecar contracts; exhaustive producer/consumer equivalence for all malformed workbooks remains unverified. S01–S22 formulas and unknowns belong to PRODUCT. No performance target or platform version invented.

## Workbook path and freshness contract (IA-01, IA-02)

Technical choice within the owner's delegated path decision; implemented in the development binary and with Linux as the current target; other platform paths below are historical design notes and require a future scope decision and verification. `--planilha PATH` selects the workbook explicitly, with relative paths resolved against the process working directory. Without the option, append `ChuteGPT/Dia de Sorte-atual.xlsx` to: Linux `$XDG_DATA_HOME` when it is absolute and nonempty, otherwise `$HOME/.local/share`; macOS `$HOME/Library/Application Support`; Windows `%LOCALAPPDATA%`. If the applicable base directory cannot be determined, explain the error and ask for `--planilha`; do not silently select a different workbook. Do not create or download a workbook on launch.

For any selected workbook, look for `.dia-de-sorte-atualizacao.json` in its parent directory. The existing updater writes exactly this name next to `docs/Dia de Sorte-atual.xlsx`. The selected workbook's frozen bytes determine the SHA-256 and parsed latest contest. A trustworthy version-2 record must be a JSON object with `version` = 2, `source` exactly `https://servicebus3.caixa.gov.br/portaldeloterias/api/resultados/download?modalidade=Dia%20de%20Sorte`, a matching lowercase SHA-256 in `sha256`, a positive integer `latest` matching the parsed snapshot, and a valid ISO calendar `date` no later than the local current date. Same local date means checked today; an earlier valid date means stale; missing, unreadable, malformed, mismatched, future-dated or unsupported records mean freshness unknown. `downloaded_at` is informational and does not override `date`. Verify using the frozen bytes, not a second changing file read. The hash and source bind metadata to contents but do not authenticate the file independently. Regardless of metadata, validate the workbook before use; a same-day check does not prove a later draw was published.

The updater only writes in the repository; it does not install or synchronize files to a user's data directory. For installed use the user supplies the official workbook at the default location or via `--planilha`. To preserve updater provenance when copying, copy the workbook and its sidecar to the same destination directory; mismatched bytes or incomplete copies must produce unknown freshness, not a false current state. An independent download or workbook without a matching sidecar is usable after the unknown-freshness warning and explicit confirmation.

Shared category-series computation and its applicability are specified in [PRODUCT](../product/series-statistics.md). Keep the statistics engine independent of terminal state, reuse typed availability/error states and preserve missing observation positions. The UI must remain responsive and cancellable while processing numerous series; completion and resource behavior need real checks. Binary64 results near bin boundaries require platform-specific validation.

## Workbook input contract

For the current official format, use the first worksheet and identify the header row by the exact required column names `Concurso`, `Data Sorteio`, `Bola1` through `Bola7`, and `Mês da Sorte`; reject missing or duplicated required names and formula/error cells in required fields. Skip wholly empty rows before the first data row and wholly empty trailing rows, but reject an empty row between data rows and incomplete nonempty draw rows. Contest is a positive integer; date is a valid Brazilian `DD/MM/YYYY` text date, a genuine Excel date cell or an ISO 8601 date string with or without a time component; balls are seven distinct integers 1..31, normalized to increasing order; month is a whole integer 1..12 or Portuguese month name after trimming, case normalization and HTML entity decoding, including março/marco. Sort by contest, require unique and contiguous IDs from 1 through the maximum, and nondecreasing valid dates in contest order; reject duplicate IDs, gaps, invalid values or dates and describe the problem. Never construct partial analysis results after invalid required data. These constraints preserve the updater's full historical snapshot expectation while accepting unordered ball cells after normalization.

Recognize optional paired winner count and rate columns from the current Caixa header for 7, 6, 5, 4 hits and lucky month. Winner counts are nonnegative whole numbers; rates are nonnegative Brazilian currency text (including `R$` and thousands separators) or finite spreadsheet numbers exactly representable to cents. Missing, malformed, negative or excess-precision optional cells become unavailable with field-specific warnings and counts, not zero; the affected calculations use their own available denominators. Unexpected extra columns do not become required. Invalid header or absent optional columns must not be interpreted positionally as another tier. The workbook bytes and unzip resource use must be bounded before expensive parsing; use the existing updater's 15 MiB compressed and 50 MiB total uncompressed limits as initial limits, reject oversized, corrupt, duplicated ZIP entries, decompression errors and unsafe archive paths without extracting files. The declared entry sizes are checked first, and the loader also counts the bytes actually inflated so an entry that understates its size cannot bypass the total limit; text cells above 64 KiB are rejected before dense materialization. The parser must not execute workbook content. Show filename and contextual error without exposing unnecessary file contents. Actual workbook formats and local date handling are implemented in `src/data.rs` and validated on the recorded Linux snapshot; see PROOF for the checks and remaining limits.

## Header consistency, description expansion and provenance cleanup (2026-11-17)

The shared screen-header renderer presents `ChuteGPT — Análise Histórica Descritiva | Fonte: <selected path> | <freshness status>` for the menu, loading, working, confirmation, result, series and error states. The header height is derived from the wrapped text using Ratatui's word wrapper plus the two borders, bounded to `area.height - 10` so the body keeps at least eight rows and the key legend two; paths that fit this budget are fully shown. If a valid path exceeds the budget, the UI must use the dedicated overflow view described below rather than imply that the clipped header is complete. The menu explanation contains only the strategy title and calculation text (plus a preflight validation failure when applicable). Each of the 22 strategies has three Portuguese paragraphs: its short definition followed by detailed calculation, input/population, historical eligibility and result-section explanations. The explanation remains keyboard-scrollable; its measured content width comes from the same Ratatui 30/70 split as rendering, so the final text remains reachable. Linux TestBackend checks cover all descriptions, screen states, a long path that fits at 55×19 and 100×24, and the explanation at both sizes. Current evidence and limitations are in [PROOF](../proof/interactive-strategies.md#narrow-terminal-header-path-closure--2026-11-17).

## Exceptional selected-path overflow (owner-selected 2026-11-17; implemented and Linux-verified)

For paths whose complete provenance header would exceed its height budget, render a short explicit overflow notice that advertises `P`. `P` overlays a dedicated view of the entire selected path, wrapped to the current terminal width and scrollable with Up/Down and Page Up/Page Down; Home/End jump to boundaries. `Esc` or `P` closes the view. Keep the overlay separate from the underlying `Screen` so preflight, loading and analysis polling continue and returning preserves the exact menu, result, warning, error or processing state. This behavior is implemented, covered by TestBackend and exercised in a Linux pseudo-terminal at 55×19; integrated checks and limits are recorded in PROOF.

## Dynamic scroll viewport derivation (2026-11-17)

The visible vertical scrolling viewports for the menu explanation (`menu_explanation_viewport_height`), category series details (`series_viewport_height`), and result details (`result_details_viewport_height`) are derived dynamically from `header_height(&display_header(app, area), area)` and the underlying screen layout via `body_area_height`. This replaces static subtraction offsets (`saturating_sub(8)` and `saturating_sub(17)`), which assumed a constant 4-row header and caused incomplete scrolling on narrow terminals when the provenance header wrapped onto 3 or more lines (header height 5 or greater).
